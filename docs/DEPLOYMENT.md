# LifeOS production deployment

LifeOS is a private, local-first application. A production process must use a
dedicated persistent data directory that is separate from application releases.

## Required environment

```dotenv
NODE_ENV=production
APP_URL=http://127.0.0.1:3001
HOST=127.0.0.1
PORT=3001
LIFEOS_DATA_DIR=/srv/lifeos/shared/data
LIFEOS_AUTH_REQUIRED=true
LIFEOS_AUTH_EMAIL=you@example.com
LIFEOS_AUTH_PASSWORD_HASH=<generated by npm run setup:auth>
LIFEOS_VAULT_SECRET=<generated and retained by npm run setup:auth>
```

Production fails closed when any required value is missing or malformed. Generate
the vault secret once, store it with restrictive operating-system permissions,
and back it up separately from application code. Changing or losing it makes the
encrypted provider credential vault unreadable.

## Storage boundary

Every persistent artifact is rooted below `LIFEOS_DATA_DIR`:

- `lifeos.sqlite`, WAL files, and migration rollback artifacts;
- `.secrets.json`;
- `qdrant.json`;
- statements, balance screenshots, and OCR binaries;
- verified backup bundles and manifests.

Do not place the live SQLite database in Git, a release directory, OneDrive, or
another file-synchronization folder. Deploy code into versioned release
directories and retain the data directory across releases.

## Startup and repair policy

Healthy startup loads and verifies existing records without altering them.
LifeOS does not seed personal goals, financial recovery rows, statement
transactions, account balances, memory snapshots, or automation history during
startup. SQLite schema migration may write only when the recorded schema version
is older; it creates a checksum-labelled pre-migration backup and reconciles the
result.

Data repair, classification, memory synchronization, backup creation, and
automation evaluation are explicit authenticated API actions. Scheduled
automation can run after startup only when enabled, and authoritative changes
remain approval-only.

## Backup and restore safety

Current backup bundles contain `lifeos.sqlite`, sanitized `state.json`,
`qdrant.json`, `statements/`, and `balance-screenshots/`. The manifest declares
these required artifacts and records a SHA-256 checksum for every file.

Restore copies the selected bundle into an isolated staging directory and
verifies its manifest, paths, checksums, SQLite integrity, and application state
before touching live data. It then creates a verified pre-restore safety backup.
Live vector and upload artifacts are moved into a rollback workspace before the
staged replacements are activated; the authoritative state is written through
the existing SQLite transaction. A reconciliation failure restores both the
previous database state and every moved file artifact. If rollback itself cannot
finish, LifeOS retains the safety backup and rollback workspace and returns
explicit operator recovery guidance instead of deleting recovery material.

## Linux and WSL OCR

Apple Vision and `sips` are invoked only on macOS. Linux and WSL skip local OCR
without spawning unsupported binaries and use NVIDIA vision when configured.
PNG and JPG screenshots are supported through that path. HEIC originals remain
saved, but Linux returns conversion guidance rather than failing or deleting the
upload.

## Release verification

Run before switching the active release:

```bash
npm ci
npm run lint
npm test
npm run docs:check
npm audit
npm run build
```

Create and verify a LifeOS backup before deployment. If startup, storage
verification, or the health check fails, leave `LIFEOS_DATA_DIR` untouched and
roll back the application release.
